## 1. What SeamXY Is

SeamXY is a fashion-tech platform that combines an AI styling concierge, virtual try-on, a bespoke maker marketplace, and a creator economy layer. It serves three distinct user classes:

- **Consumers** — discover and style outfits, use AI concierge personas, book custom garments, trade closet items
- **Suppliers** (retailers, tailors, designers) — list products, manage orders, connect their e-commerce integrations
- **Stylists / Creators** — build a portfolio and subscriber base, take RFQ-driven client projects, earn via subscriptions and tips

## 4. Authentication — Three Separate Tracks

```
Customer            /api/v1/auth/*          users table
                    session cookie          requireUser middleware

Supplier            /api/v1/supplier/*      supplier_accounts table
                    JWT / session           authenticateSupplier middleware

Admin               /api/v1/admin/*         admin_users table
                    separate login          requireAdmin middleware + audit log
```

Every sensitive API route gates on one of these three middleware functions. Admin actions write to `audit_logs` (before/after JSON diff).

## 8. AI Architecture

- **Model:** Claude claude-opus-4-5 via `@anthropic-ai/sdk`
- **Mechanism:** Tool Use — the server defines tools (product search, wardrobe lookup, measurement read) that Claude calls mid-conversation
- **Personas:** 9+ named AI stylists stored in `ai_personas` (name, style philosophy, system_prompt). Each session selects one persona; the system prompt is injected before every message.
- **Context injection:** User measurements, style profile, and closet items are injected into the session context at creation time
- **History storage:** Full message history stored as JSONB in `ai_chat_sessions.history`
- **Stylist training:** Human stylists can submit `ai_training_responses` to tune persona behavior

## 9. Virtual Try-On Pipeline

```
User photo upload (S3 presigned URL)
        ↓
MediaPipe Pose  — landmark extraction in browser
        ↓
TPS Studio      — thin-plate-spline garment warp (server-side)
        ↓
Result stored   — tryon_results + S3
        ↓
Share link      — tryon_shares → /try-on/shared/:shareCode (public)
        ↓
AR overlay      — /ar-try-on (MediaPipe live camera feed)
```

## 10. Monetization Model

| Stream | Mechanism |
|---|---|
| Pro subscription | Stripe recurring, `subscriptions` table |
| Creator subscriptions | Fan subscribes to stylist tiers via Stripe |
| Creator tips | One-off Stripe payments |
| Affiliate commissions | Click + conversion tracked, retailer revenue share |
| Supplier SaaS | `supplier_subscriptions` — basic / pro / enterprise |
| Gig platform fee | Percentage of `gig_quotes` on completion |

Stripe webhooks update subscription status in real time. The `pricing_configs` table lets admins adjust tier pricing without code deploys.

## 14. Known Sharp Edges

- **`.migration-backup/`** is the authoritative snapshot of routes and schema. The `lib/db` package is the forward-going schema home, but migration-backup is what the running API server actually uses today.
- **Three separate auth sessions** run in parallel — a customer cookie, a supplier session, and an admin session. Middleware is not interchangeable between tracks.
- **Try-on `.map()` loops** remain in several team-deck slide files. They render correctly but are not visually editable via the slide editor's click-to-edit. This is a known trade-off for data-driven slides.
- **Port is env-driven** — all Vite dev servers read `process.env.PORT`. Hard-coding a port breaks the preview proxy.
- **Orval codegen** — after any OpenAPI spec change, run `pnpm --filter @workspace/api-spec run codegen` before touching the frontend; the generated hooks and Zod types will be stale otherwise.
